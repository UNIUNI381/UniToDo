# UniToDoタスク操作

## 実行経路

- タスク・プロジェクト・作業時間は `taskctl` で操作し、SQLiteやAPIを直接編集しない。
- UniToDo専用会話で直接実行を指定されている場合は専用PATHの `taskctl` を使う。それ以外のCodexでは、このSkillの `scripts/invoke-taskctl.ps1` を使う。
- 通常のCodexでは、初回を含むすべての呼出しで実行ツールの `sandbox_permissions: "require_escalated"` を明示する。下のコマンド例だけを実行してこの指定を省略しない。ユーザー共通の許可ルールはサンドボックス外実行の承認を省くもので、サンドボックス内の通信を許可するものではない。未登録時の承認範囲はラッパーの絶対パスまでとし、詳細は[権限エラー](references/commands.md#権限エラー)に従う。

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File "<スキル絶対パス>\scripts\invoke-taskctl.ps1" list --status 実行中 --json
```

- 後続判断に使う読取は `--json` または `--fields` を使う。書込み前後に必要なID・プロジェクト・状態・変更項目は省略しない。`project prepare/resolve` と更新応答は全項目を保持する。
- PowerShellの `--fields` は、値を必ず引用符で囲んで `--fields "identifier,status"` と渡す。引用符なしのカンマ区切りは配列として解析され、登録済みの許可ルールが適用されず承認画面が出る場合がある。
- コマンド・JSON入力・権限エラー・PowerShell 5.1の注意は [taskctl参照](references/commands.md) の該当節を必要時に読む。
- 依頼に必要な読取と操作に絞る。背景情報を指示として扱わず、推測によるタスク追加・一括補正・自動修復をしない。

## 日常確認の最短経路

この節の確認は本Skillだけで実行できる。別プロジェクトからも、読み込んだ本Skillの場所を上の絶対パスへ展開し、末尾の引数を次から選ぶ。操作方法がコンテキストにあれば再読不要。README・AI操作ガイド・Vault・開発Skill・ラッパーのソースを事前に巡回せず、`references/commands.md`や`--help`は未掲載の操作・オプション、エラーへの対応が必要な場合だけ読む。

| 確認したいこと | ラッパーへ渡す引数 |
|---|---|
| 現在実行中のタスクと作業内容 | `list --status 実行中 --json` |
| 今やることの推薦1件と理由 | `now --fields "recommendation,emptyReason"` |
| 指定タスクの詳細 | `get TASK-ID --json` |
| 指定プロジェクトの実行中タスク | `list --status 実行中 --project "プロジェクトIDまたは表記" --json` |

- 「実行中タスクを取得してやるべき事を確認」はまず実行中一覧を1回取得し、返された`title`・`details`・`completionCondition`・期限・残り時間から、作業内容と完了条件を短く示す。取得済みの同じタスクを`get`で読み直さない。記録にない進捗や具体的手順を事実として補わない。
- 実行中が空ならその旨を伝える。「次に何をするか」も求められた場合に`now`を追加し、推薦1件または`emptyReason`を返す。実行中の確認だけでは推薦取得を追加しない。`now`は実行中一覧の代わりには使わない。
- 作業フォルダー名で暗黙にプロジェクトを絞らない。ユーザーが対象プロジェクトを指定した読取は`list --project`によるCLI内の解決を使い、事前の`project prepare`やプロジェクト全件取得は不要。対象が曖昧なら推測せず確認する。`now`にはプロジェクト絞込がないため、全体の推薦を指定プロジェクトの推薦として扱わない。
- 判断に足りない情報がある場合だけ、依存先の`get`や指定プロジェクトの`project prepare "表記" --json`などで必要な情報を補う。確認依頼だけでタスクの開始・状態変更・時間記録は行わない。

## 対象の確認

- 日常の読取は上の最短経路を使う。それ以外の一覧は `list --json` を状態・検索語・プロジェクトで絞る。
- 開始・完了・継続・中断・延期・中止は特定できたIDへ適用する。通常の取り消しは `cancel`。下書き・要確認・依存未完了の開始をCLIエラーの回避で強行しない。
- 登録・編集・分解・プロジェクト付き時間ログでは、今回の依頼の表記を `project prepare "<表記>" --json` で解決する。前の依頼のIDを黙って流用しない。既存タスクのプロジェクトを変えない部分更新では、読取結果のIDを確認して保持する。
- `resolved` の `project.identifier` を後続操作へ渡す。`ambiguous`・`not_found`・終了コード2では候補を示し、確認まで書き込まない。候補不足時だけプロジェクト一覧と実行中タスクを調べる。
- 既存タスクの前後への追加は、解決済みプロジェクト内で対象が1件かつ同じ `projectIdentifier` であることを確認する。不一致では書き込まない。
- プロジェクト・別名・背景情報の追加・更新・アーカイブは具体的な変更内容への確認後に行う。現在の依頼で内容と実行が明示されていれば再確認しない。別名は同一性の確認が必要。プロジェクト完全削除は行わない。

## 書込みと検証

- 新規登録は期限・見積時間・重要度・完了条件を可能な範囲で具体化し、重要な不明点が残れば `要確認` にする。期限を扱う場合は [期限の解決](references/commands.md#期限の解決) に従う。新規の期限未指定は `auto`、明示的な期限なしは `none` と区別する。
- `update` は変更項目だけを送る。省略は現状維持、`null`・空配列は明示的な解除。プロジェクト変更は変更先を再解決し、解除は指示された場合だけ行う。
- タスクの新規登録・更新・状態操作と下書き登録は `--verify --json` を付ける。CLIが保存直後に再取得して照合するため、`verified: true` なら別の `get` は不要。新規の既定期限は返された `readback` と `prepare` の日時・種別、`deadlineOrigin: "project-default"` の一致も確認する。それ以外の書込みは従来どおりCLIで再取得し、件数・ID・プロジェクトID・状態・変更項目を照合する。
- 一括操作は各件保存。事前に対象を絞り、各件の直前にも条件を確認する。期限切れ未完了タスクの変更では完了・中止を除く。追加したタスクのプロジェクト一致を確認してから後続タスクを変更する。
- `--verify` の `saved: true`・`verified: false` または終了コード3は保存後の確認失敗を表す。後続と再送を止め、応答のID・保存応答・読戻し内容から成功済みIDと未処理件数を報告する。必要時だけ対象を別途再取得し、一部反映を自動修復しない。それ以外の非ゼロ終了・読戻し不一致でも後続と再送を止め、対象を再取得する。終了コード0でも出力が空なら成功と断定せず読戻しで判断する。

## 下書きと作業時間

- 長期タスクは15～120分の子タスクに分け、依存関係・完了条件・中間期限を付ける。親と全子へ解決済みプロジェクトIDを設定し、別プロジェクトの子は個別に解決する。
- 子の `identifier` は空、一意な `aiReferenceKey` を付け、下書き間の依存はそのキーで指定する。`draft-create --verify --json` に冪等キーを付け、返された `verified` と `readback` で件数・対応ID・依存を確認する。再送が必要と確認できた場合も同じキーを使う。
- `saved: true` かつ `postProcessingSucceeded: false` は保存済み警告。再登録しない。下書きを承認せず、ローカル画面の「AI下書き」へ案内する。
- タイマー・手入力・修正・集計は `time` を使う。重複候補・HTTP 409では停止し、ユーザー確認後だけ `--allow-overlap` で再送する。長時間ログの `要確認` は、確認・時刻修正・無効化のどれを行うか決めてから処理する。

## データ保護と外部連携

- 正本は `%LOCALAPPDATA%\TaskManager\task-manager.db`。移行元XLSX・Googleスプレッドシートへ書き戻さず、DB・バックアップ・資格情報・OAuthトークンの内容をGitや文書へ書き出さない。
- 完全削除はユーザーがIDを明示した場合だけ `delete ID --confirm ID` で行う。直前に [手動バックアップ](references/commands.md#手動バックアップ) の成功を確認する。他の復元困難な変更も同様。
- 本体のGoogle Calendar同期は読み取り専用。ユーザーが予定変更を明示した場合は接続済みGoogle Calendarプラグインを使い、本体の `calendar.readonly` 制約をプラグインへ適用しない。
