# 頒布と受取人セットアップ

## 目的と前提

`UniToDo`は、ソースコードと設計資料をGitHubの公開リポジトリで提供し、利用者向けの検査済みZIPをGitHub Releasesで頒布します。noteなど外部の記事から案内する場合も、Google Driveへ複製せずGitHubのReleaseページへ誘導します。公開リポジトリのURLは確定後に利用者向けREADMEへ記載します。更新サーバー、自動更新、Plugin Marketplaceは使用しません。

このVaultで「頒布版」は、`artifacts/distribution`配下で生成し、GitHub Releaseへ添付するZIPを指します。GitHubがタグごとに自動生成する`Source code (zip)`と`Source code (tar.gz)`は、自己完結型ランタイムを含まないため頒布版ではありません。現環境へ反映するための発行・インストールも頒布版生成に含めません。

対象はWindows 10/11の`win-x64`です。利用だけなら.NETランタイムは不要です。ソースを変更する場合だけ.NET 10 SDK 10.0.303以降を使用し、通常のビルドとテストはWindows PowerShell 5.1またはPowerShell 7で実行します。頒布ZIPの再生成だけはPowerShell 7を使用します。

## 頒布物の構成

頒布ZIPには次を含めます。

| 場所 | 内容 |
|---|---|
| `最初にお読みください.txt` | 展開後にCodexへ入力する最初のプロンプト |
| `Install.ps1` | 発行済み本体、CLI、Codex Skillのユーザー単位インストール |
| `runtime/` | 自己完結型`TaskManager.exe`、`taskctl.exe`、実行依存ファイル |
| `runtime/licenses/` | インストール後も確認できるMIT、第三者一覧、.NET SDK付属文書、実行時パッケージ付属文書とハッシュ索引 |
| `LICENSE`、`THIRD-PARTY-NOTICES.md`、`licenses/` | 独自部分のMIT License、第三者コンポーネント一覧と原文、依存検査用一覧 |
| `AGENTS.md` | Codex依頼の振分けとシステム開発規則 |
| `.agents/skills/` | `taskctl`による日常操作の正本と、システム更新時のVault・Git整合を担うリポジトリ内Skill |
| `src/`、`tests/`、`scripts/`、`integrations/` | 受取人が改良するソースと検証・頒布スクリプト |
| `docs/` | AI操作ガイドと設計Vault |

元の`.git`履歴は含めません。受取人が履歴管理を必要とする場合は、個人データを含まない展開後フォルダーで新しいGitリポジトリを作成します。

## 頒布ZIPの作成

開発ツリーのルートで次を実行します。

```powershell
pwsh -NoProfile -File .\scripts\create-distribution.ps1
```

実行にはPowerShell 7が必要です。Windows PowerShell 5.1では、テストと発行が完了しても、同環境に存在しない`System.IO.Path.GetRelativePath`をallowlistコピー処理が呼び出すため、ZIP生成前に停止します。同じ5.1環境で再試行せず、PowerShell 7でスクリプト全体を実行し直します。

スクリプトは次の順で処理します。

1. `scripts/test.ps1`でビルド、テスト、静的検査を行う。
2. PowerShell 7の`pwsh -NoProfile -File ./scripts/publish.ps1`で自己完結型`win-x64`を発行する。
3. `artifacts`配下に空のステージングディレクトリを用意する。
4. 明示したソース、文書、Skill、受取人用スクリプトだけをコピーする。
5. 発行済みファイル、SDK付属文書、実行時パッケージ付属のLICENSE・NOTICE・Third-Party Notices全文を`runtime/`へコピーする。
6. 発行済み`.deps.json`と`licenses/dependencies.json`の名前・バージョンが完全一致することを検査する。
7. `package-legal-files.json`と収録文書のSHA-256が、頒布ルートと`runtime/licenses/`の両方で一致することを検査する。
8. 禁止された個人データや一時ファイルがなく、必須ライセンス原文が揃っていることを検査する。
9. 検査済みステージングだけをZIPへ圧縮する。

ワークスペース全体を直接ZIP化してはいけません。`.gitignore`は手動ZIPへの混入を防がないため、必ず空のステージングへallowlist方式でコピーします。

## GitHub公開とRelease作成

公開リポジトリには追跡対象のソース、テスト、文書、Skillだけを送信します。`artifacts/`はGitで追跡せず、頒布ZIPはReleaseの添付資産として提供します。公開前とRelease作成時は次の順で確認します。

1. [ローカルGit管理](09_ローカルGit管理.md)に従い、公開対象の履歴、コミットメール、追跡ファイル、リモートURLを検査する。
2. `scripts/test.ps1`が成功した変更だけを公開ブランチへ記録する。
3. `scripts/create-distribution.ps1`で頒布ZIPを新規生成し、個人データ検査、依存関係、ライセンス原文の検証を通す。
4. リリース対象コミットへ`v<メジャー>.<マイナー>.<パッチ>`形式のタグを付ける。
5. GitHubで下書きReleaseを作り、同じ版の変更点、対象OS、導入方法、既知の制約を記載する。
6. `UniToDo-win-x64.zip`と、そのSHA-256をReleaseへ掲載する。
7. 添付資産と説明を確認してからReleaseを公開し、ログアウト状態でもZIPを取得できることを確認する。

GitHubが自動生成するソースアーカイブや、ワークスペースを手動圧縮したZIPをRelease資産として案内しません。安定性を確認していない版はpre-releaseとして公開します。

## 頒布へ含めないもの

次は頒布ZIPに含めません。

- `.git/`、`.codex/`、`.dotnet/`
- `data/`、既存の`artifacts/`、`bin/`、`obj/`
- SQLite本体、WAL、SHM、バックアップ
- `credentials.json`、OAuthトークン、ログ
- 実タスク、顧客、予定、作業ログ、プロジェクト背景
- 作成者固有のCodexタスクID

頒布検査でこれらを1件でも検出した場合は、ZIPを作成せず失敗させます。

## 受取人の最初の操作

受取人の開始手順とCodexへ送る依頼文は [最初にお読みください](../../最初にお読みください.txt) を参照します。環境とインストールの影響を確認して `Install.ps1` を実行し、導入後に `taskctl now --json` で疎通を確認します。

`Install.ps1`はインストール前に独自部分のMIT License、第三者一覧、同梱.NETランタイムのライセンス原文の場所を表示します。続いてデスクトップへ`UniToDo`ショートカットを作成し、ユーザー単位のWindowsタスク`UniToDo Watchdog`を登録します。このタスクがログオン時に監視親を起動し、監視親自体の異常終了も最大3回復旧します。Codexからインストールしても監視親はCodexの実行ジョブに所属しないため、Codexのタスク切替でUniToDoが巻き添え終了しません。旧名の`TaskManager.lnk`と`LocalTaskManager Watchdog`は更新時に削除します。

Codexは最初に`AGENTS.md`、このVaultの入口、本文書、`manage-local-tasks`を読みます。個人設定、Google Calendar、音声入力、プロジェクトやタスクの新規登録は、受取人の希望を確認してから行います。

導入時は設定画面の「追加バックアップ」を案内し、別の物理ディスクへの保存を推奨します。既定はOFF・保存先未指定とし、作成者の保存先を引き継ぎません。受取人が利用する保存先と有効化の希望を確認し、別ディスクがなければOFFを維持します。有効化後は手動バックアップの成功を確認します。保持・復元方法は[READMEのバックアップ](../../README.md#バックアップ)を参照します。

## Google Calendar OAuthの初期設定

Google Calendar連携を希望する場合、Codexは次の要点を前提に受取人とGoogle Cloudの現行画面を確認しながら案内します。作成者のOAuth認証情報は再利用せず、受取人が自分のGoogleアカウントとGoogle Cloudプロジェクトで作成します。

1. Google Cloudでプロジェクトを作成または選択し、[Google Calendar API](https://console.cloud.google.com/apis/library/calendar-json.googleapis.com)を有効化する。
2. [Google Auth Platform](https://console.cloud.google.com/auth/overview)でアプリ名、サポート用メール、対象ユーザーを設定する。個人のGoogleアカウントは通常`External`を選び、公開ステータスが`Testing`なら連携する本人をテストユーザーへ追加する。`Internal`は対象のGoogle Workspace組織内だけで使う。
3. `Google Auth Platform > Clients > Create Client`でアプリ種別`Desktop app`のOAuthクライアントを作成し、JSONファイルをダウンロードする。APIキー、サービスアカウント、`Web application`クライアント、リダイレクトURIの手入力は不要。
4. UniToDoの設定画面でダウンロードしたJSONを`credentials.json`として選択し、「Googleへ接続」からブラウザ認証した後に予定を同期する。UniToDo本体が要求する権限はGoogle Calendarの読取専用だけとする。

`Testing`中のExternalアプリでは、Googleの現行仕様上、同意とリフレッシュトークンが7日で期限切れになります。継続利用で認証が切れる場合は、Codexが[Audienceと公開ステータス](https://support.google.com/cloud/answer/15549945)の現行仕様を確認し、本番公開とGoogleの確認手続の影響を説明してから受取人に選択を求めます。画面名や要件が異なる場合は、Google公式の[Google Auth Platformの初期設定](https://support.google.com/cloud/answer/15544987)と[OAuthクライアント管理](https://support.google.com/cloud/answer/15549257)を優先します。

ダウンロードしたJSON、保存済み`credentials.json`、OAuthトークンはそのPCの受取人だけが使用し、Git、頒布ZIP、文書、メールへ含めません。

## Codex Skill

リポジトリ内の`.agents/skills/manage-local-tasks`は日常のタスク操作規則の正本です。対象確認・書込み検証・データ保護は `SKILL.md`、コマンド・JSON・期限の詳細は `references/commands.md` に置き、`AGENTS.md` に依存せず使えます。`Install.ps1`でこのSkillだけをユーザー領域へコピーすると、別の作業フォルダーを開いたCodexからも同じUniToDoを操作できます。

`.agents/skills/update-task-manager-system`は、このリポジトリの開発変更で実装、設計Vault、ローカルGitを同じ変更単位に保つSkillです。リポジトリ内だけで使用し、ユーザー領域へはコピーしません。

Skillの正本はリポジトリ内です。Skillの変更だけでは頒布ZIPを生成しません。ユーザーが頒布版の生成を明示した場合だけ`scripts/create-distribution.ps1`で作り直し、受取人は自分の環境で必要に応じて再インストールします。

## 受入確認

頒布前に次を確認します。

- .NETランタイム未導入の標準Windowsユーザーで`Install.ps1`を実行できる。
- Windowsタスク`UniToDo Watchdog`が実ユーザーで登録され、ログオンまたは手動実行後に`/api/v1/health`が応答する。
- 初回起動時に空のユーザーデータが作成される。
- 所有者固有のCodexタスクIDが初期設定へ入らない。
- Codexがrepo Skillを認識し、SQLiteを直接操作せず`taskctl`を使う。
- 受取人が.NET 10 SDK導入後に`scripts/test.ps1`を実行できる。
- ZIP展開後の全ファイルを検査し、DB、資格情報、トークン、実タスクを含まない。
- ZIPルートと`runtime/licenses/`にライセンス一式とパッケージ付属文書があり、発行依存関係が`licenses/dependencies.json`、文書のSHA-256が`package-legal-files.json`と一致する。
- 公開リポジトリの履歴に個人メールアドレスや秘密情報がなく、意図したブランチとタグだけが公開されている。
- GitHub Releaseに検査済み頒布ZIPとSHA-256があり、ログアウト状態でダウンロードできる。
